# A股模拟盘 · 1万元

一个会自动交易、自动记账、自动复盘的 A 股模拟盘。初始资金 ¥10,000，
严格执行 A 股交易规则，策略自行设计并持续迭代。

> **位置：`E:\TradingSim`**（已从 C 盘迁出，避免占用系统盘）
> 双击 **`打开模拟盘.bat`** 即可刷新数据并打开可视化看板。

## 每天的运行节奏

**你不需要每天打开 AI，也不需要盯盘。** 工作日三个任务自动跑：

| 时间 | 任务 | 干什么 |
|---|---|---|
| 14:45 | 盘中执行与复盘 | 拉行情 → 全天逐分钟重放 → 判定信号 → 记账 → 写复盘 |
| 15:05 | 收盘定稿 | 重放全天走完 14:50 强平 → 检查是否留隔夜仓 → 存静态快照 |
| 周五 15:30 | 周报与迭代评审 | 统计表现 → 查规则偏离 → 判断样本是否够格调参 → 出周报 |

**唯一前提**：这些时间点 WorkBuddy 客户端要在运行，否则任务会跳过（不补跑）。

### 谁决定什么

| 事项 | 谁做 | 说明 |
|---|---|---|
| 买不买、买什么 | 程序 | 按 `strategy.py` 规则硬判定，没有主观空间 |
| 记账、费用、T+1、涨跌停 | 程序 | 规则引擎把关 |
| 写复盘、算统计 | 程序 | 自动完成 |
| **改参数** | **必须等人评审** | 样本门槛：累计 ≥20 笔 且 ≥10 个交易日 |

为什么不让程序自己调参：现在只有 2 笔有效样本，任何"优化"都是拟合噪音。
让策略每天追着当天盈亏改参数，几周后你会得到一个完美解释过去、但毫无预测力的模型。
所以参数迭代写死了硬门槛，`engine/weekly.py` 里 `MIN_TRADES=20 / MIN_DAYS=10`。

### 出问题怎么发现

- 看板右上角圆点：绿=数据新鲜，橙=在用缓存，红=服务连不上
- 收盘定稿会检查隔夜仓，有就标【⚠️ 过夜风险】
- `runner.py` 每次启动自动扫历史仓位，发现非当日建仓立即告警
- 周报检查三类偏离：过夜持仓 / 单日超频 / 单日大亏（>1%）
- 每次运行写 `state/heartbeat.json`，`selfcheck.py` 据此判断有没有漏跑

### 电脑常开方案（当前采用）

系统跑在本机，**电脑不开机就不会执行**。选了这条路，就要保证金定时任务的条件：

**最省事的做法**：右键 `设置不休眠.bat` → **以管理员身份运行**。
它一次性设好四条策略（插电时永不睡眠 / 永不休眠 / 硬盘不关 / 合盖不动作），
并把「显示器 15 分钟关闭」保留下来省电——显示器关了不影响任务。

手动等效命令（管理员 PowerShell）：

```powershell
powercfg /change standby-timeout-ac 0      # 插电时永不睡眠
powercfg /change hibernate-timeout-ac 0    # 插电时永不休眠
powercfg /change disk-timeout-ac 0
powercfg /change monitor-timeout-ac 15     # 显示器可以关，不影响任务
```

**笔记本合盖**是单独一项，`/change` 改不到，必须设 SUB_BUTTONS/LIDACTION：

```powershell
powercfg /setacvalueindex SCHEME_CURRENT SUB_BUTTONS LIDACTION 0
powercfg /setactive SCHEME_CURRENT
```

三个最容易翻车的点：

| 风险 | 后果 | 对策 |
|---|---|---|
| 睡眠/休眠 | 14:45 任务跳过 | 上面四条命令 |
| 合盖睡眠（笔记本） | 同上 | 合盖设为「不采取任何操作」 |
| Windows 更新重启 | WorkBuddy 没起来，全周不跑 | 设置「活动时间」，并把 WorkBuddy 加入开机自启 |

**怎么自查**：任意时候跑一次 `python engine/selfcheck.py`，看「任务心跳」那行。
超过 96 小时没记录会报警，说明某个环节断了。

> 自动化**不补跑**。漏一天就是漏一天，第二天的重放只覆盖当天，
> 补不回昨天的交易记录。心跳机制的作用是「让你知道漏了」，不是「帮你补上」。

## 实时更新是怎么做的

**静态页面的死穴**：`dashboard/index.html` 是文件，生成那一刻取了数就定了。
浏览器打开后它就是一张照片，不会自己变——页面上「数据更新 11:21」会一直停在 11:21。

`engine/serve.py` 补上了这一环：

```
后台线程 ──→ 内存状态 ──→ HTTP ──→ 页面 JS（每 4 秒取一次）
   ↑                                     │
   └── 东财接口（受 2.2s 节流约束）  ←────┘ 只读内存，零额外请求
```

关键点在**节奏分离**：

| 环节 | 频率 | 说明 |
|---|---|---|
| 批量报价 | 每 20 秒 | 一次请求拿全部 10 只 |
| 分时数据 | 轮转，约 35 秒一圈 | 每轮只取一只，摊平节流 |
| 页面轮询 | 每 4 秒 | 只读服务内存，不打接口 |

页面刷得再勤也不会把接口打爆，因为真正联网的只有后台那一个线程。

启动瞬间用本地缓存填满表格（`bootstrap()`），不等网络，打开即见 10 行；
后台随后逐只替换成实时数据，右上角会从「N 只缓存」逐步变成实时。

```bash
python engine/serve.py                 # 默认 8899，自动开浏览器
python engine/serve.py --port=9000
python engine/serve.py --no-browser    # 只起服务
```

### 三道保险（2026-10-19 补）

只靠「用户记得先双击 bat」是靠不住的——事实上就出过事：服务没在跑，
用户点开 `index.html`，看到的是一张 17 分钟前的照片，然后合理地生气了。
所以现在有三道保险：

**1. 静态页自己会连服务。** `index.html` 里始终带着轮询脚本，打开时按顺序试
`/api/state` → `127.0.0.1:8899` → `8900` → `8901` → `8902`，谁通用谁。
服务端回了 `Access-Control-Allow-Origin: *`，所以 `file://` 打开的页面也能跨源取数。
**双击静态文件 = 实时页**，不再是快照。

**2. 连不上会明说。** 五个地址全失败时，页头弹红色横幅
「未连接实时服务 · 页面上是冷快照，数字不会变」，时间戳改成「已断开」、状态点转红。
不会再有「看起来正常、其实不动」这种状态。

**3. 服务会自己把快照写回磁盘。** 后台每 30 秒重写一次 `dashboard/index.html`。
所以哪怕服务刚挂，F5 一下看到的也不会是几十分钟前的数。

加上单实例保护：`serve.py` 启动时先探测 8899–8918，已经有本程序在跑就只打开浏览器、
不再起第二个（两个实例会各自拉一遍行情，白烧请求还可能在两个端口给出不同画面）。

## 交易规则：T+0 与 T+1（2026-10-20 修正）

这条曾经写错，代价很大，所以单独列出来。

上交所《ETF 相关问题》第 3 条：

> 目前，国内部分 ETF 品种支持 T+0 交易，比如债券 ETF、黄金 ETF、跨境 ETF、
> 货币 ETF；但是，**股票 ETF 实施 T+1 交易**。

**不能因为它是 ETF 就当成 T+0。** 池子里的 510/512/588/1599xx 全部跟踪 A 股
股票指数，一律 T+1——当天买入当天卖不掉。

`broker.is_t0_etf()` 按代码段判断：

| 代码段 | 品种 | 规则 |
|---|---|---|
| 511xxx | 债券 ETF / 货币 ETF | T+0 |
| 513xxx | 跨境 ETF | T+0 |
| 518xxx | 商品 ETF（黄金） | T+0 |
| 1590xx | 深市货币 ETF | T+0 |
| 159920 | 恒生 ETF（跨境） | T+0 |
| 其余（510/512/588/1599xx） | 股票型 ETF | **T+1** |

### 池子是刻意混合的

| 类型 | 标的 | 含义 |
|---|---|---|
| T+1 | 沪深300、中证500/1000、创业板、科创50、红利、上证50、深证100 | 买入即过夜，次日才能卖 |
| T+0 | 中概互联网(513050)、恒生科技(513180)、黄金(518880) | 支持日内回转 |

只做 T+0 等于逃避真实约束——账面收益好看，但那是「只挑容易的那半」。
两类一起做，回测才能回答这套逻辑在真实规则下站不站得住。

### 代码里怎么落实

**「该不该卖」和「能不能卖」必须分开**，这是核心：

```python
can_sell = pos["overnight"] or broker.is_t0_etf(code)
strategy.decide(..., can_sell=can_sell)
```

不能卖时 `decide` 直接返回 HOLD，不产生任何卖出意图。混在一起的后果是
「策略说卖、账上也卖了，现实里根本没有这个成交」——今天就是这么错了一整天。

runner 尾盘强平也受 `can_sell` 约束；卖不掉时记一条 `LOCKED` 事件明说
「T+1 锁定，转次日续管」，而不是静默留仓。

回测里隔夜仓的处理：次日把 `entry_idx` 置 -1，等价于「一开盘就超过持有上限」，
按市价了结。另外**权益必须算「现金 + 持仓市值」**，只算现金的话过夜仓会让
日盈亏凭空少一大块。

### 修正前后的差距

同一份 5 日数据、同一套参数：

| | 收益 | 说明 |
|---|---|---|
| T+0 假设（错的） | +0.59% | 当天买当天卖 |
| T+1 真实（对的） | **-2.86%** | 买入必须过夜 |

一次 -4.14% 的隔夜跳空，就吃掉两次日内小赚。

## 云端看板（手机 / 平板）

```
https://ashare-sim-dashboard.app.workbuddy.link/
```

打开网址就能看，不需要电脑开机、不需要装任何东西。手机浏览器直接可用。

### 它是什么

一份**只读镜像**，不是第二个交易系统：

| | 本地 `E:\TradingSim` | 云端 `E:\TradingSim_cloud` |
|---|---|---|
| 下单 / 记账 | 有（`runner.py`） | **无** |
| 行情 | 实时拉 | 实时拉 |
| 账本 | 实时写入 | 发布时上传的快照，只读 |
| 用途 | 真实运行 | 展示 |

云端**永远不会**产生交易，也不会回写本地账本。两边是「同一个账本的两种读法」，
不是两个账户。

### 数据边界（这条必须记住）

**行情是实时的，账本是快照的。** 云端没有交易进程，`account.json` / `trades.csv`
停在最后一次发布那一刻。所以页头有一条青色「云端镜像」说明，写明
**持仓与成交记录截至 X**——不写清楚会让人把镜像显示的持仓当成实时持仓。

当前是空仓（10000 元现金），账本本来就不变，所以现在两者完全等价。
**一旦产生第一笔持仓，就必须在成交后重新发布一次**，否则手机上会看不到这笔交易。

### 同步机制（两条路，别混）

| | 干什么 | 触发 | 延迟 |
|---|---|---|---|
| `push_cloud.py` | 只推三个**账本文件**到云端 `/api/sync` | runner 每次跑完 | 几秒 |
| `sync_cloud.py` | 目录对齐 + 触发**重新发布** | 收盘定稿 15:05 | 一天一次 |

**为什么要有 push**：发布是「上传整个目录 + 重启服务」，只能人工点。
而成交随时发生，等收盘才更新的话，手机上看到的就是几小时前的仓位——
2026-10-20 下午就为这个问过「为什么显示可入场却没买」。

**为什么还要发布**：push 改的是运行中的文件，容器一旦重启就回到部署包的旧状态。
每天收盘把最新账本打包进去，第二天重启也有数据。

#### push：成交后几秒到手机

云端 `serve.py` 多了一个 `POST /api/sync`。令牌放在 `X-Sim-Token` 头里，
每次只替换 `account.json` / `trades.csv` / `equity.csv`，先写 `.tmp` 再 `rename`，
不碰代码、不重启服务。账户结构不完整直接 400 拒绝——这里没有事务，覆盖了就回不来。

```bash
python engine/push_cloud.py           # 有变化才推
python engine/push_cloud.py --force   # 无条件推
python engine/push_cloud.py --check   # 只看会不会推
```

**幂等靠流水签名**：`trades.csv` 的 sha256 前 16 位存进 `state/.pushed`，一样就
一个请求都不发。所以 runner 每 60 秒调一次也几乎没有开销。

推送失败**不影响交易**：`runner` 里这段包了 `try/except`，异常全吞，
下一轮签名仍不一致会自动补推。日志在 `state/push.log`。

注意本机有出口代理，`push_cloud.py` 里显式 `ProxyHandler({})` 直连——
带代理会被拦成 501。

#### 发布：sync_cloud 那一层

`engine/sync_cloud.py` 负责把本地目录对齐到云端副本，并且**只在真的变了的时候才推**：

```bash
python engine/sync_cloud.py           # 需要就同步
python engine/sync_cloud.py --check   # 只看，不动文件
```

判断依据是**内容哈希**，不是修改时间——`broker` 每次存快照都会重写
`account.json`，即使数字没变 mtime 也会变。拿时间比会把「没变化」误判成
「有新成交」，于是天天白发布一次、白重启一次沙箱。

输出最后一行是给自动化任务看的：`NEED_PUBLISH=1` 表示文件已更新、需要重新发布才
生效；`=0` 表示一致，什么都别做。

自动化「A股模拟盘·收盘定稿 15:05」的第 5 步会跑它，然后回读
`/api/state` 核对持仓数与净值，对不上会写进 journal，而不是假装同步成功。

**发布参数有个坑**：`startCmd` 必须显式写 `python engine/serve.py`。
省略的话平台会去找 `main.py`，直接报
`can't open file '/workspace/main.py'`，启动失败、线上链接当场挂掉。
（2026-10-20 第一次发布就踩了这个。）

### 为什么要单独一份目录

不是复制粘贴图省事，是刻意的隔离：

- 云端那份改过 `serve.py`（读 `PORT`、绑 `0.0.0.0`、跳过单实例探测和写回），
  本地那份不能有这些改动——本地要的就是「双击就能起、自动开浏览器」。
- 两边共用同一套渲染代码（`dashboard.py` / `theme.py`），改样式时**两份都要同步**，
  否则云端和本地会长得不一样。

云端模式是靠环境变量判断的：平台注入 `PORT` → 进入云端分支。
不带 `PORT` 时行为与本地版完全一致，所以本机也能直接调试云端代码。

### 为什么本地拉不到分时、云端反而能

本机的出网走一个 HTTP 代理，它把腾讯分时域名 `web.ifzq.gtimg.cn` 拦成 501，
而批量报价域名 `qt.gtimg.cn` 是通的。结果就是本地「有价格、没分时」，
只能靠 `state/cache/` 里的缓存兜。云端沙箱直连外网，两个域名都通，
实测 10/10 只标的实时分时齐全。

这不是代码问题，本地重启也不会好，是网络环境的事。

### 移动端适配

宽表格（策略监控 9 列）在窄屏会顶出卡片，而 `body` 是 `overflow-x:hidden`，
多出来的列会被直接裁掉、连滚动条都看不到。所以每张表包了一层 `.tscroll`，
900px 以下自己横向滚，列宽保得住。

### 入口兜底（云端专属）

任何**不带扩展名**的路径都回主页，只有 `.js/.css/.png` 这类资源缺失才 404。

起因是应用面板里打开显示 `Not Found`，而 `curl` 直连 shareLink 是 200 / 40KB、
进程 pid 一直没变（没有冷重启）——说明服务没挂，是预览入口拼的路径跟 `/` 对不上。
硬 404 只会让人看到一个纯文本 `Not Found`，分不清「服务挂了」还是「路径没对上」。

单页应用对未知路由回首页本来就是标准做法，何况这页的 CSS/JS 全内联，没有外部资源要区分。
这一条只改云端副本，本地版不需要——本地永远是访问 `/`。

### 开盘 20 分钟会显示「开盘N分」

**这不是故障。** 策略的 `earliest_entry` 是 09:50，开盘 20 分钟内本来就不交易
（VWAP 在累计均价还不稳的时候没有参考价值）。分时每分钟一根，09:33 只有 3 根。

早先 `metrics_from_ticks` 写的是「不足 20 根一律返回 None」，显示层又把 None 一律
标成「无分时」——于是每天开盘前 20 分钟，十只标的齐刷刷显示「无分时」，
报价却还在跳。**数据明明在，只是不够做判断。** 把「没数据」和「数据不够」混成
同一句话，最容易被读成接口挂了（我自己就被骗过一次，去查了半天代理）。

现在拆成三级：

| 分时根数 | 显示 |
|---|---|
| 0 根（接口失败 / 无缓存） | 无分时 |
| 1–19 根 | 开盘N分（同时给出 VWAP 与偏离） |
| ≥ 20 根 | 正常判断（差 X% / 可入场 / 待反弹…） |

3 分钟动量需要回看 3 根，不足 4 根时给 `None` 显示 `—`，
**不拿 0.0 冒充「动量持平」**——0.0 会流进 `ok_mom` 的比较，
等于凭空宣称一个不存在的读数。

## 自动运行

### 定时任务（模拟盘相关）

| 任务 | 时点 | 干什么 |
|---|---|---|
| **常驻交易循环**（本地进程） | 交易日 09:30-15:00 每 60 秒 | 真正的分钟级执行，`启动自动交易.bat` |
| 盘前自动体检与自愈 | 交易日 09:20 | 跑 doctor，把环境问题修在开盘前 |
| **盘中自动交易循环**（自动任务） | 交易日每小时 | 兜底：进程没开时补上，有成交就同步云端 |
| 盘中执行与复盘 | 交易日 14:45 | 尾盘再确认一次 |
| 收盘定稿 | 交易日 15:05 | 结算、强平、体检、同步云端 |
| 周五周报与迭代评审 | 周五 15:30 | 统计、样本门槛、参数评审 |
| **每日代码自审** | 每天 16:00 | 读代码找设计缺陷，不等用户提醒 |

### 为什么是「每小时」而不是「每 15 分钟」

调度器只接受单个 `BYHOUR` / `BYMINUTE`——传多值会直接报错，传了单值在
`FREQ=HOURLY` 下又被忽略，实际就是「距上次运行 + 1 小时」。所以 15 分钟粒度
在这套调度器上表达不出来。

**但这不影响账本。** `runner.py` 不是「这一刻盯盘」，它是**从当日开盘重放到当前时刻**，
逐分钟判断信号、按那一分钟的真实价成交。两轮之间隔了一小时，这一小时里的信号
也不会漏——重放会补上。频率只决定「你多久看到一次结果」，不决定「成交对不对」。

### 常驻循环：真正的分钟级执行（2026-10-20 补）

调度器做不到 15 分钟粒度，那就绕开它——跑一个常驻进程：

```
双击 启动自动交易.bat   后台常驻，交易时段每 60 秒重放一次
双击 停止自动交易.bat   停掉
```

对应 `runner.py --loop 60`。只在 `09:30-11:30 / 13:00-15:00` 真正执行，其余时间睡眠；
每轮独立拿锁，单次崩溃不会把锁带走；单轮异常只打印不退出。记录在 `state/loop.log`
（一行一轮：时间、标的数、权益、持仓数、事件数），stdout 落到 `state/loop_out.log`。

**为什么必须有它**：定时任务整点才看一次，09:50 出的信号 10:46 才被看见。
账本不会错（重放会补成交），但那是「事后记账」，不是「实时执行」。

**这里踩过一个坑，记下来防再犯**：`market.fetch_trends` 默认 `ttl=600`。
循环每 60 秒调一次，数据却 10 分钟才换一份——进程在跑、日志在滚、页面在刷，
看到的却是 10 分钟前的分时。典型的「看起来在工作，实际在空转」。
所以 `--loop` 会把 `ttl` 压到 `interval - 5`。凡是"定时任务 + 带缓存的数据源"，
都要问一句：缓存的过期时间比执行间隔长吗？

### pythonw 与 .bat 的两个坑

1. **`pythonw` 没有控制台，`sys.stdout is None`**，任何 `print` 都会抛
   `AttributeError` 直接把循环打死——而进程还在，看起来"在跑"，实际早就死了。
   `_loop` 开头会把两条流落到 `state/loop_out.log`。（已实测确认这个值为 `True`。）
2. **`.bat` 必须 CRLF + 纯 ASCII**。LF 换行会让 cmd 把命令截断，报出
   `'st' 不是内部或外部命令` 这种看不出所以然的错；UTF-8 中文注释在 GBK 代码页下乱码。
   `doctor.py` 会检查这一条——而且现在会**真的动手修**（见下）。

### 2026-10-20 修的一个「谎报」缺陷

`doctor.check_bats` 原来发现 bat 编码有问题时，会调 `make_launcher.py` 然后直接
报「已重写」。但 `make_launcher` 只重建它自己列表里那几个脚本，**用户新加的 .bat
它根本不碰**。结果是：报告说修好了、文件没动、下次体检照样报、用户还以为修过了。

现在改成跑完 `make_launcher` 后**自己复查再就地修**（LF→CRLF、非 ASCII 降级成 `?`），
修完仍不合格才报 `CRIT`。原则还是那句：能不能修好要说实话。

### 并发锁（这条很关键）

定时任务会重叠：盘中循环、收盘定稿、手动补跑可能在同一分钟触发。
`runner` 的流程是「读账户 → 重放全天 → 写账户」，两个进程同时跑就是经典的
lost update——后写的覆盖先写的，流水少一笔、现金对不上，**而且不会报错**，
要等第二天 doctor 才发现。

所以 `runner.py` 用 `O_EXCL` 建 `state/runner.lock`，拿不到就打印
「另一个 runner 正在运行，本次跳过」并退出。被强杀留下的僵尸锁超过 10 分钟自动失效。

看到那句提示是**正常的**，不要重试，更不要手动删锁文件。

## 自查与自愈

系统自己找 bug，不等用户提醒。两个脚本分工不同：

| | 回答什么问题 | 依赖真实数据？ |
|---|---|---|
| `selfcheck.py` | 文件在不在、接口通不通 | 是 |
| `doctor.py` | **不变量还成不成立** | 部分 |
| `selftest.py` | 极端情况下会不会算错 | 否，全用合成行情 |

### 为什么需要「不变量」

`selfcheck` 只能回答「东西还在吗」。它查不出真正会咬人的问题：
账本少算一分钱、流水断了号、页面写的是三天前的数、某次改动让回测
结果悄悄漂移。这些都不报错，只会安静地给出错误结论。

所以 `doctor.py` 换一套标准——**不变量**：无论跑多少次都必须成立的等式。

| 不变量 | 破了说明什么 |
|---|---|
| 现金 + 未核销批次成本 = 本金 + 已实现盈亏 | 记账逻辑错了 |
| `cash_after` 逐笔链式相加 = 当前现金 | 流水被改过或写漏 |
| 序号 1..N 连续 | 有笔交易没记上 |
| 持仓数 ≤ 1 | 资金被拆到两只标的上 |
| 买入整百 / 卖出不超持仓 / 非竞价时段无成交 | 违反 A 股规则 |
| 费率 = min(万2.5, 5元) + 印花税 + 过户费 | 成本算错，直接影响收益结论 |
| 同一份缓存 + 同一套参数 → 回测结果不变 | 改代码时策略行为漂移了 |

重放必须用**和券商完全相同的算法**（FIFO 分批、卖出费摊到批次）。
用平均成本法重算会和券商对不上，然后检查器自己就是错的——
这种「看起来对」的检查比没有更危险。

### 分级与自愈

| 级别 | 含义 | 自动处理 |
|---|---|---|
| `OK` | 正常 | — |
| `FIX` | 发现问题，已修好 | 服务没跑→拉起；页面是旧版→重写；bat 编码错→重生成；残留 pid→清理 |
| `WARN` | 可疑，需要人看 | 不动 |
| `CRIT` | 违反硬规则 / 账务对不上 | **不擅自改钱**，只报告 |

账务类问题一律不自动修。钱算错了应该让人看，而不是让程序「猜一个正确值」
写回去——那会把一个可查的错误变成一个查不到的错误。

### 端到端自测（`selftest.py`）

真实账本经常是空的（今天 0 笔成交），空账本上任何检查都「通过」——
那是假的安全感。所以自测在**临时目录**里用合成行情跑，可以放心制造极端情况：

1. 券商规则：非整百、资金不足、午休时段、持仓上限
2. 费率：ETF 免印花税、5 元佣金下限、股票卖出印花税
3. 资金恒等式：连续买卖后仍然成立
4. `--dry` 不改任何账本文件（**曾经真会写，把今天的数据覆盖到昨天那行**）
5. 同一天跑两次，账户完全一致（幂等）
6. 过夜仓：不开第二只，且按日内规则平掉
7. 尾盘缺数据：兜底强平必须生效（**曾经会漏，仓位安静过夜**）
8. 无未来函数：决策不看 `i` 之后的数据
9. 检查器自测：篡改过的账本必须被抓到

### 自动跑

- **每个交易日 09:20** 盘前体检与自愈（自动化任务）
- **每个交易日 15:05** 收盘定稿后自动跑一次 `doctor.py`
- 有 CRIT 才需要人介入；账务类只报告不擅改

## 已知问题与修复记录

### 2026-10-19 · `--dry` 试跑把今天的净值写进昨天那一行

**现象**：无。这是自查时用确定性实验发现的，不跑实验永远看不到。

**根因**：`broker.snapshot()` 无条件落盘，而 `--dry` 模式不调用 `roll_day`，
`acc["today"]` 还停在昨天。于是「只推演不记账」的试跑把今天的权益
写到昨天那一行上，**覆盖掉昨天真实的净值**。

**修复**：`snapshot(..., write=False)`；`runner` 里 dry 时传 `write=execute`，
并且无论如何先把日期推到今天。试跑从此真的只读。

### 2026-10-19 · 已有过夜仓时又开了第二只

**现象**：无。同样是自查发现的——`runner` 用局部变量 `pos` 记录当前仓位，
每次运行都从 `None` 开始。一旦开盘就有过夜仓（前一日没平掉），
它会认为自己是空仓，去开第二只。

**修复**：
- `broker` 加 `MAX_POSITIONS=1`，在 `buy()` 里硬拦（资金只够摊薄一只）
- `runner` 开盘时把已有持仓接回 `pos`，按日内规则平掉而不是无视

### 2026-10-19 · 持仓标的尾盘没数据 → 强平不执行 → 仓位过夜

**现象**：无。这是最危险的一条，因为它只会在数据缺口时发生，而那时没人看盘。

**根因**：强平判断写在「该分钟有 tick」的分支里。标的尾盘停牌或数据断流时，
那一分钟根本进不到判断，`for` 循环跑完仓位还在。

**修复**：两层兜底。循环内——该分钟没 tick 但已过 14:50 就用最后一根价平仓；
循环后——仍有仓位且时间已过强平时刻，再补一次最终平仓。

### 2026-10-19 · 东财限流拖垮整个系统 → 接入腾讯为主源

**现象**：`runner.py` 单次要 20 秒以上，看板经常「实时 2 只 / 缓存 8 只」，
实时服务的圆点长期是橙色（在用缓存）。根因是东方财富接口的分钟级限流，
配合全局 2.2 秒节流 + 5 次重试退避，一个完整刷新周期被拖到分钟级。

**修复**：新增腾讯两个 HTTP 接口作为主源。

```python
TX_MINUTE = "https://web.ifzq.gtimg.cn/appstock/app/minute/query?code=sh510300"
TX_QUOTE  = "http://qt.gtimg.cn/q=sh510300,sz159915"
```

关键发现：腾讯分时返回 `0930 4.224 115873 48944755.00`，
即 **时间 / 价格 / 累计量(手) / 累计额(元)**，与东财 `trends2` 完全同构。
VWAP 直接算 `累计额 / (累计量 × 100)`，实测 4.239，东财同刻 4.2388，误差在 4 位小数内。

配套改动：
- `fetch_trends_tx()` / `fetch_quotes_tx()` 新增，返回结构与原函数一致
- `fetch_trends()`：当日（ndays=1）优先腾讯，失败落回东财，再失败用缓存
- `fetch_quotes()`：腾讯 → 东财 → 本地快照，三级降级
- **节流按源拆分**：`_LAST_TS` 改成 dict，东财 2.2s、腾讯 0.6s
- `serve.py` 节奏收紧：`TREND_IDLE` 1.2→0.2，`QUOTE_EVERY` 20→10

**实测结果**：

| 场景 | 前 | 后 |
|---|---|---|
| runner 一次执行 | 20.8s | **5.9s** |
| 看板生成 | 12.3s / 实时 2 只 | **0.77s / 实时 10 只** |
| 实时服务 | 实时 2 缓存 8 | **实时 10 缓存 0** |

**保留东财的原因**：腾讯只给当日分时，回测需要多日历史，那部分只有东财
`trends2?ndays=N` 能给。所以双源并存，不是替换。

### 2026-10-19 · 页面时间停在 11:21，不会实时更新

**现象**：看板能打开，但右上角「数据更新」一直停在生成那一刻，价格也不动。

**根因**：架构问题，不是 bug。`dashboard.py` 产出的是**静态 HTML 文件**。
浏览器加载后文件内容不再变化，没有任何东西去重新取数。

**修复**：新增 `engine/serve.py` 常驻服务。

- `ThreadingHTTPServer` 提供 `/`（页面）和 `/api/state`（JSON）
- 后台线程按 `QUOTE_EVERY=20s` 刷新批量报价、按轮转顺序补分时
- 页面内嵌 JS 每 4 秒 `fetch('/api/state')`，用 `data-code` / `data-k`
  定位单元格**就地改文字**，不整页刷新、不闪屏
- 右上角小圆点：绿色=数据新鲜，橙色=在用缓存，红色=服务连不上
- `dashboard.render(live=True)` 才注入轮询脚本，静态模式完全不受影响

实测连续采样：`11:28:04 → 11:28:26`，510300 从 `4.246 → 4.243`，
实时标的数 `0 → 5` 递增，确认数据在流动。

### 2026-10-19 · 双击后黑窗口卡住不动

**现象**：修好编码后脚本能跑了，但 cmd 窗口停在
`[1/2] Refreshing dashboard data...` 十几秒甚至几分钟，看起来像死机。

**根因**：看板要给 10 只标的**逐只**拉分时，而 `market.py` 有全局 2.2 秒节流；
接口限流时 `_get` 还会重试 5 次、每次退避 2/4/6/8 秒。最坏情况
10 × (2.2 + 20) ≈ 3 分钟以上，全部串行阻塞。

**修复**：给数据层加「时间预算」机制。

- `market.set_budget(seconds)` 设置截止时间（`time.monotonic()` 计时）
- `_throttle` / `_get` 在**会超出预算**时立即抛 `BudgetError`，不再傻等
- `dashboard.pool_status(total_budget=13)` 分配预算：批量报价最多 5 秒，
  剩余时间逐只补分时；预算耗尽即停止联网，剩余标的走 `load_cached_trends()`
- 页面右上角按来源分三种标注，一眼能分清是「没联网」还是「联了没拿到」：
  `· 离线快照（未联网）` / `· 全部读本地缓存（本轮联网未成功）` / `· N 只读缓存`

实测：`--budget=6` 用 5.5 秒返回（实时 1 只 + 缓存 9 只），
`--offline` 用 0.77 秒，完整版 12.3 秒封顶。**再也不会无限卡住。**

同时新增 `快速查看.bat`（离线秒开），启动窗口会先打印
`max 13s, falls back to cache on timeout`，让人知道在等什么。

### 2026-10-19 · 双击启动脚本报「'1' 不是内部或外部命令」

**现象**：双击 `打开模拟盘.bat` 弹出 cmd 窗口，连续报
`'1' 不是内部或外部命令` / `'ngSim' 不是内部或外部命令` / `'鹕版…' 不是内部或外部命令`。

**根因**：脚本文件被保存成了 **UTF-8 + LF 换行**。`cmd.exe` 解析批处理时：

1. 按单字节读取，遇到 UTF-8 多字节中文（`echo 正在刷新数据...`）字节流错位；
2. 只认 CRLF，纯 LF 会让它把一行的长度算错，从而把 `cd /d E:\TradingSim` 从中间切断，
   残片 `1`、`ngSim` 就被当成命令去执行了。

**修复**：`engine/make_launcher.py` 以 **纯 ASCII + CRLF** 重写脚本，提示语全部改英文，
去掉 `chcp 65001`。重新生成后两个文件均为 `CRLF=23  bare_LF=0  非ASCII=0`，实测退出码 0。

**教训**：给 Windows 写 `.bat`，内容必须是 ASCII、行尾必须是 CRLF。
这条约束已写进 `make_launcher.py` 的文件头注释，以后改启动脚本请走这个生成器，不要手写。

## 看板包含什么

- **资金流场**（主视觉）：中心是账户净额，四周环形排布 10 只标的

- **策略监控**：10 只标的的 VWAP 偏离、低点反弹、动量，以及"距入场还差多少"

## 资金流场怎么读

```
              ┌── 512880 ──┐            ← 环形 = 标的池（现价 / 涨跌 / 偏离）
      518888 ─┤             ├─ 510500
              │   ┌─────┐   │
    159915 ───┤   │ 资金 │   ├─ 159915   ← 中心 = 总资产 / 今日 / 累计
              │   │ 中心 │   │
      512480 ─┤   └─────┘   ├─ 510300
              └── 512170 ───┘
```

| 视觉 | 含义 |
|---|---|
| 红色粒子 **从节点流向中心** | 这只持仓在赚钱 → 资金流入账户 |
| 绿色粒子 **从中心流向节点** | 这只持仓在亏钱 → 资金从账户流出 |
| 节点不发光 | 未持仓，没有资金往来 |
| 节点绿色呼吸 | 策略判定"可入场"，信号亮了 |
| 节点红色描边 | 当前持仓中 |
| 中心光晕呼吸 | 跟随流入/流出方向着色，钱在动就有反馈 |
| 空仓时缓慢雷达弧 | 表示系统在跑，但没有资金流动（不误导） |

粒子由 `canvas` 绘制（`dashboard.py` 里的 `FLOW_JS`），一帧几十个点，比 DOM 动画省得多。
节点位置用**角度 + 百分比**在服务端算好，不依赖 JS 定位，静态 HTML 打开也是对的。

示意图见 `dashboard/资金流场示意.png`（用假数据渲染，仅说明效果）。

## 规则引擎约束（broker.py）

| 规则 | 实现 |
|---|---|
| T+1 | 股票当日买入不可卖；ETF 支持 T+0 |
| 涨跌停 | 主板 ±10%、创业/科创 ±20%、ST ±5%、北交所 ±30% |
| 交易单位 | 买入 100 整数倍；卖出可全平零股 |
| 交易时段 | 9:30–11:30、13:00–15:00 |
| 佣金 | 万 2.5，最低 5 元，双边 |
| 印花税 | 0.05%，卖出、仅股票 |
| 过户费 | 0.001%，仅股票、双边 |
| 滑点 | 买 +1 tick / 卖 -1 tick（ETF 0.001、股票 0.01） |

## 策略概要

**T+0 日内均值回归**：价格跌破当日 VWAP 0.8% 以上、并从 15 分钟低点反弹 0.3% 时买入，
相对入场价 +0.5% 止盈、-0.4% 止损、20 分钟时间止损。

完整逻辑与迭代记录见 **交易思路.md**。

## 数据源

**双源架构**：腾讯为主，东财为备。切换开关是 `market.PREFER_TX_INTRADAY`。

| | 腾讯 | 东方财富 |
|---|---|---|
| 当日分时 | ✅ 一次请求拿全天，格式同构 | 有分钟级限流 |
| 历史多日 | ❌ 只给当日 | ✅ `trends2` 支持 ndays |
| 批量报价 | ✅ 一次拿 10 只 | ✅ 但常被限流 |
| 节流间隔 | 0.6 秒 | 2.2 秒 |

腾讯分时返回 `HHMM 价格 累计量 累计额`，VWAP = `累计额 / (累计量 × 100)`，
与东财 `trends2` 的 `avg` 字段算法一致，上层逻辑无需改动。

**改造前后对比**（同一台机器、同一时段）：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| `runner.py` 单次执行 | 20.8s（且常降级） | **5.9s** |
| `dashboard.py` 生成 | 12.3s，实时 2 只 | **0.77s**，实时 10 只 |
| 实时服务覆盖率 | 实时 2 / 缓存 8 | **实时 10 / 缓存 0** |

历史多日数据（回测用）仍走东财 `trends2`，因为腾讯只提供当日。
所以 `engine/warmup.py` 仍然需要，且只能慢速跑。

### 评估过但没接的源

**腾讯金融科技 NeoData**（已连接，工具 81 个）。结论：**不接**。

判断标准只有一条：能不能解决当前最大的瓶颈——**历史分钟样本只有 5 个交易日**。

| 它的能力 | 本项目需要吗 |
|---|---|
| 财报三表 / 估值分位 / 研报评级 / 龙虎榜 / 两融 / 期货外汇宏观 | ❌ 日内 VWAP 均值回归只用 现价、当日累计均价、当日成交量 |
| 90 个数据信号、口径统一、可复现 | 是优点，但用不上 |
| 分钟线 `fund_quote` | ⚠️ `limit` 上限 2000，一天 240 根，**最多 8 天**，救不了 60 天的需求 |
| 与其它来源混拼 | ❌ 它的说明明确禁止；会拆掉现有的腾讯/东财双源容错 |

成本对比：现方案零鉴权、单只 0.6 秒、连续跑了多天没被限流。

**什么时候回头用**：策略转成事件驱动（`events`/`dividend`/`block_trade`）、
跨市场对冲（`futures_quote`/`forex`）、或需要指数成分权重做精细筛选
（`index_stocks`/`index_industry`）。详见 `交易思路.md` 第九节。

> 注：本会话里 neodata 的 MCP 工具没有注册进工具索引（连接状态是 connected，
> 但 `mcp__neodata__*` 全部报 not found），以上结论基于其能力清单，不是实测。
> 若将来要真用，需重启会话让工具加载。

### 日线历史（250 日）

`state/cache/daykline_pool_250.json` 存了池子 10 只 ETF 的 250 个交易日日线，
用于评估标的属性（振幅、流动性、收盘区间位置）。**注意：日线属性判断必须用

## 幂等性说明

`runner.py` 每次运行都会把账户恢复到「当日开盘状态」重新推演，因此
同一天内重复运行不会重复记账。结果只取决于当日的分钟数据。
